Le parcours d'une offre, de React à SQLite

Cette page suit la requête qui permet à un utilisateur autorisé d'ouvrir la page des offres, depuis le routage frontend jusqu'aux lignes enrichies renvoyées par la base de données.

Parcours principal

01 · ACCÈS

App et navigation

App.tsx vérifie la session et canListOffers. NavBar expose le lien Offres aux profils concernés.

02 · REQUÊTE

Page et hook

OffersPage appelle useOffers. Le hook déclenche le chargement, gère l'annulation et redirige sur une réponse 401.

03 · HTTP

Service et proxy

offers.service.ts envoie GET /api/offers. Vite retire /api et relaie vers le backend sur /offers.

04 · API

Contrôle backend

Express authentifie le token, autorise canListOffers, puis le contrôleur délègue au service métier.

05 · DONNÉES

Service et SQLite

La visibilité est appliquée selon le rôle. Le repository joint entreprises, années et périodes, trie les offres et renvoie les résultats.

Frontend

  • Rendu : OfferTable.tsx affiche le titre, l'entreprise, l'année académique, la période et le statut.
  • Contrat : guards.ts vérifie la forme de la réponse; offer.ts définit les codes de période et de statut.
  • États : OffersPage.tsx distingue chargement, erreur, liste vide et liste remplie.
  • Libellés : labels.ts traduit notamment P1, P2 et OTHER.

Backend

  • Authentification : authenticate.ts valide le token et recharge l'utilisateur depuis SQLite.
  • Autorisation : authorize.ts et permissions.ts bloquent les profils non autorisés avec une erreur 403.
  • Visibilité : offers.service.ts adapte les résultats au rôle : toutes les offres pour l'administrateur, publiées pour l'étudiant, propres offres pour le déposant.
  • DTO : offer.mapper.ts limite la réponse publique aux champs nécessaires à l'interface.

La requête de données

offers.repository.ts construit une requête préparée sur offers. Elle joint companies pour le nom abrégé, academic_years pour l'année et periods pour le code de période. Les conditions actuelles portent sur le statut et l'identifiant du contact déposant, puis le tri se fait par année académique décroissante et date de création décroissante.

La relation offers.period_id est déjà présente dans 001_initial.sql. Les périodes et leurs dates sont alimentées par academicData.ts; les offres de démonstration les utilisent via offersData.ts.

Ajout d'un filtre par période

Hypothèse retenue : filtrer par le code de période existant (P1, P2 ou OTHER), et non par une plage de dates arbitraire. Cette évolution ne nécessite donc pas de migration SQLite.
